## Spacing Scale

Established in Phase 1 (01-CONTEXT.md Claude's Discretion). Reused across all phases.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, button borders |
| sm | 8px | Compact element spacing, form field gaps |
| md | 16px | Default element spacing, section gutters |
| lg | 24px | Section padding, card margins |
| xl | 32px | Layout gaps, major component spacing |
| 2xl | 48px | Major section breaks |

**Exceptions (Phase 3 specific):**
- Contact action buttons (Call, Email): Full-width on phones (min-height: 44px touch target), side-by-side on tablet+ with gap of `md` (16px)

## Component-Specific Contracts

### Page Layout Structure (Mobile-first)

**On phones (< 768px):**
1. Page heading: "Contact & Hours"
2. **Contact actions section:** Call and Email buttons (stacked, full-width, 44px height)
3. **Address section:** Full address + "Get directions" link
4. **Hours section:** Weekly table, then upcoming exceptions (if any)
5. **Contact form section:** Name, email, message fields + submit button
6. **Map section:** Placeholder (if no consent) or iframe (if consented)

**On tablet/desktop (≥ 768px):**
- Two-column layout:
  - **Left column:** Contact actions, address, hours
  - **Right column:** Contact form (sticky optional)
- **Full-width section below:** Map

### Form Component (`ContactForm.astro`)

**Attributes:**
- No-JS fallback: `<form action="https://api.web3forms.com/submit" method="POST">` redirect to same page (or custom redirect from data file)
- JS behavior (fetch/AJAX): Inline success/error message; form fields retain user input on error; submit button disabled during send
- Spam protection: Hidden `botcheck` honeypot field (Web3Forms standard); optional hCaptcha if available on free tier and mobile-friendly (Phase 3 D-50, 03-CONTEXT.md)
- Field validation: HTML5 `required` + `type="email"`
- Accessibility: `<label>` for each field, linked via `for` attribute; `aria-live="polite"` or `role="status"` on result message; submit button announces to screen readers

**Styling details (from Phase 3 Claude's Discretion, 03-CONTEXT.md D-52):**
- Input/textarea styling: Border using secondary color (#EEEEEE), 4px corner radius, padding `sm` (8px horizontal) + 12px vertical, focus state uses accent outline
- Submit button: Full-width on mobile, auto-width on desktop; background: accent (#0066CC), text: white, padding: `sm` (8px) horizontal + 12px vertical, border-radius: 4px, min-height: 44px
- Form spacing: `md` (16px) between fields, `lg` (24px) before submit button

### Map Component (`Map.astro`)

**Consent placeholder (initial state):**
- Tinted block: Secondary color background, `aspect-ratio: 4 / 3` on phones (< 768px) or `16 / 9` on tablet+ (≥ 768px), width 100%
- Content: Centered map pin icon (inline SVG, 24px or 32px), address text (small font), "Show map" button (styled as accent CTA)
- Consent note: Text below button, small font (14px)

**After consent:**
- Replace placeholder with Google Maps iframe: `<iframe src="https://maps.google.com/maps?q=[url-encoded-address]&output=embed" title="Map of [shop name]" loading="lazy" referrerpolicy="no-referrer-when-downgrade" width="100%" style="aspect-ratio: 4 / 3; border: none;" ...></iframe>` on phones, or `style="aspect-ratio: 16 / 9; border: none;"` on tablet+
- **Note (Phase 3 researcher to confirm in 2026):** The keyless Google Maps embed form (`maps.google.com/maps?q=...&output=embed`) should be verified to confirm it still works without an API key. If Google has changed this form's behavior, pick the closest keyless alternative (per CONTEXT.md D-08); do not introduce an API key. Aspect ratios are set in the component's CSS with a media query, not via inline styles.
- Dimensions: Responsive via `aspect-ratio` CSS property (4:3 mobile, 16:9 tablet+), full-width container

**No-JS fallback:**
- Placeholder always renders; "Get directions" link works independently
- No attempt to load iframe without JS

**Accessibility:**
- Iframe has `title="Map of [shop name/address]"` for screen readers
- Placeholder button has `aria-label="Load map for [address]"` or similar

### Hours Component (reusing Phase 1 logic)

**Weekly hours table:**
- Rows: Mon–Sun, with today highlighted (optional, Phase 3 D-48)
- Columns: Day, Hours (or Day, Open time, Close time if split hours are common)
- Closed days: Display "Closed" instead of time
- Split hours: Display both periods if applicable, e.g., "10am–12pm, 2pm–6pm"
- Client-side computation: "Today's row" is calculated using `Date` API in the shop's time zone (reuse Phase 1 utilities)

**Upcoming exceptions (if present):**
- Section title: "Upcoming changes" (only if data contains upcoming exceptions within ~30–60 day window)
- Format: Short list, e.g., "Dec 25: Closed" or "Dec 26: 11am–5pm"
- Styling: Subtle background color (secondary or neutral tint), padding `sm`/`md`, border-left with accent color as visual anchor

- Color: Inherit from text or use token (e.g., `--color-accent` for pins, `--color-success` for checkmarks)
- Viewbox: "0 0 24 24" (standard 24x24 grid)
- No drop shadows or complex effects

## Copywriting Tone & Voice

- **Professional & trustworthy:** Retail business context; plain language, clear next steps
- **Action-oriented:** CTAs use active verbs ("Call", "Email", "Send message", "Show map")
- **Error messages:** Problem + solution (e.g., "Email is required—please fill it in")
- **Success:** Warm and brief (e.g., "Thank you! We'll be in touch soon.")
- **No jargon:** Avoid "form submission" or "geolocation"; use "Send message" and "map"
